# 能力架构规则

## 1. 围绕责任设计，而不是围绕操作拆文件

共同维护同一含义、状态和生命周期的行为放在同一责任主体。编排连接能力、传递上下文、调度和汇总，不拥有所有业务实现。

分开问三个问题：

- **拆职责**：是否存在不同的状态所有者、验证方式或变化原因？
- **参数化**：是否存在真实、合法且反复出现的用户选择？
- **做复用**：是否已有第二个实际调用者，或明确的可独立交付需要？

三个答案不必相同。单文件工具不需要为了扩展性建插件框架；多阶段业务也不必每阶段单独建 Skill。

## 2. 语义契约与实现分离

调用方描述“要什么结果”，实现方决定具体工具、供应商和文件布局。输入/输出保留必要的身份、证据和错误状态，不泄漏私有对象给下游。

可变供应商确有需求时，分成：能力契约 → 服务适配器 → 用户运行配置。新增来源优先新增适配器，而不是给主流程再写一个服务商特例。没有替换需求则直接实现，保留清楚接口即可。

跨 Skill 资源引用不能假设 `../另一个Skill` 总是存在。以当前工程激活列表解析名称，或由 CLI 参数显式注入文件。共享规则只有一个维护者，不能复制到每个消费者后各自漂移。

## 3. 区分意图、计划、执行与结果

用户意图规定目标和授权；方案是 Agent 对目标的回答；证据记录实际观察，不与解释混写。

可恢复的长任务分清：可重用方案、一次运行请求、执行尝试、产物、当前进度。简单任务无需把每项存成独立文件；只有重试、并发或审计需要时才实体化。

一次执行部分失败，不抹去已有结果。超时只说明观察结束，不证明底层任务失败。先核查当前状态，再按身份和依赖恢复缺失部分，不无条件重跑全流程。

## 4. 谁拥有事实，谁接收修改

源内容归作品，通用代码归 Skill，用户选择归配置，临时运行状态归运行目录。UI、索引和报告是投影，不成为第二份权威。

编辑必须回写所有者；没有可靠逆映射时提供只读视图，不制造看似可编辑的副本。安装能力不等于激活能力，技术成功不等于用户认可。

## 5. 按变化与证据决定失效

身份匹配后才复用。对发布/制作等任务，输入指纹、任务身份、实际现场状态分别核验；文件 hash 证明内容一致，不证明历史真实、发布成功或用户认可。

重试应具备可观察状态、有限重试条件和停止边界。新的外部副作用先查是否已经发生，避免重复发布、重复计费和覆盖陌生草稿。

## 6. 从真实问题渐进披露

入口让首次使用者知道能完成什么、需要什么、失败怎么办。按当前问题读参考，不强制线性走完所有章节。高级扩展不污染基础路径。

主观表达由 Agent/人判断；稳定格式、路径校验、合并、去重辅助、API 读写等交给程序。不要用关键词检查冒充内容质量，也不要每次用语言模型重算确定公式。

## 本工作区的落点

| 所有者 | 负责 | 不负责 |
| --- | --- | --- |
| topic-radar | 来源采集、来源状态、事件聚类、时效证据 | 自动决定作者要做什么 |
| topic-engine | 与当期定位匹配、角度和评分、选题卡 | 硬编码账号定位或抓取各来源 |
| topics | 每日推荐结果、待选状态、用户选择与作品关联 | 可重用采集/评分源码 |
| works | 已选核心命题、内容、制作、交付及分发记录 | 保存所有未选热点作为作品 |
| 工作区维护 CLI | 编号、索引、幂等 pick、关联与元数据一致性 | 生成业务内容或复制 Skill 实现 |

用户 pick 后保留原选题的证据和去向，不从推荐历史删除；重复 pick 返回已有作品。此表是边界设计，不代表相关命令已经实现。
