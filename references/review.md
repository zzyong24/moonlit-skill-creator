# 审查、整改与可分发性

## 审查记录

每个 Skill 留一个结论，包含用途、适用检查、证据位置、问题、采取动作、验证与剩余风险。原规则清晰有效则写“保留，无需修改”；禁止脱离真实痛点做纯话术润色、堆砌打勾检查表或拆碎健康结构，不能以修改了多少文件衡量整改。

优先级：P0 是秘密/权限/破坏性风险；P1 是主流程失效、数据所有权或恢复错误；P2 是耦合、迁移、入口负担或验收虚化；P3 是不影响使用的呈现问题。扫描器只提供候选证据，人工判定是否成立。

## 检查问题

- 使用者能用自然语言发现能力吗？相邻任务是否会误入？
- 输入缺失时问的问题是否真的改变决定？能否用合理默认值、具体示例和现有配置省掉重复确认？
- 模板是否服务于理解与交付，还是变成固定配额或死板结构反过来绑架不同题材？
- 谁拥有结果与状态？是否有双写、历史副本、兄弟目录假设？
- 把整个目录搬走后，必要资源、解释器与依赖还找得到吗？
- 初始化、重跑、部分失败、超时、恢复分别发生什么？
- 外部写入是否有本次授权、身份确认和成功证据？
- 主流程是否携带大段历史复盘或不相关模式？
- 验收标准是否全部可观察、可核验，还是用“高级、生动、有冲击力、有获得感”等模糊形容词充当完成条件？
- 脚本是否只是关键词打分却被宣称为语义判断？
- 配置是否偷偷固定用户、供应商、价格、平台或账号？

## 改动与验证

先确认维护源和实际激活版本；保留工作树已有更改。需要前后独立对照或未跟踪文件不可恢复时，在扫描目录外留基线。窄修可用精确补丁，不要求整库备份。

按风险选择验证：结构检查 → 本地单元/契约测试 → 陌生目录首次使用 → 失败恢复 → 同任务前后对照 → 真实环境验收。实质改动行为、默认策略或产出结构时，用同一最小代表性任务（必要时加相邻反例）对比改前基线与改后产物，核验返工点是否减少且无能力退化；错字、死链等窄修免做形式化 A/B。不得因为“需要实测”越过用户授权进行真实发布。

文案和视觉由用户评审最终表达；模型评分不能替代。没有独立执行者时写“作者自测，独立验证未完成”。未获真实受众或线上运行反馈前，所有完播、转化、阅读感受等效果结论强制标记【待真实上线验证】，严禁把离线样本差异宣称为效果已证实。兼容性区分实测、静态检查、未验证。

## 分发

面向人的说明讲清用途、安装方式、自然语言例子、依赖、配置、数据发送方、测试和限制。不要编造未发布仓库地址或未经测试的安装命令。

月明 Skill 准备独立 GitHub 仓库时，另按 [独立仓库与品牌规范](repository-branding.md) 对齐 Skill/仓库命名、README 首图、安装路径和发布边界。旧合集 `zzyong24/moonlit-skills` 已于 2026-11-17 归档；维护和安装使用对应已核验的独立仓库。本机旧目录与运行快照保留，未核验入口不自动迁移，不再向旧合集同步。

依赖可随包分发的需检查许可证；外部 Skill 用名称、版本/来源和必要资源契约声明。不把本机绝对路径当安装说明。

运行产物、个人配置、凭据、浏览器资料、依赖安装目录、缓存和外部评测 workspace 不进入包。公开前做成熟的当前树及历史秘密扫描；轻量审计不覆盖这一步。

交付时区分：已创建、已审计、已整改、已激活、已实际试用。不能用“验证通过”涵盖所有状态。
